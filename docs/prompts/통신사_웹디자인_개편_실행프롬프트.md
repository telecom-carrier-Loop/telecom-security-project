# L∞P 통신사 웹 디자인 개편 — 실행용 프롬프트

아래 지시를 읽고 이 프로젝트의 고객·관리자 웹 UI를 실제로 수정하라. 설명이나 시안 제안만으로 끝내지 말고, 기존 기능을 보존하면서 파일 수정과 검증까지 수행하라. **커밋·푸시·PR 생성·실제 서버 배포는 하지 않는다.**

## 1. 작업 대상과 목표

- 프로젝트: `C:\Users\user\Desktop\Project\telecom-security-project`
- 브랜드: **L∞P(루프)**, 멤버십 브랜드: **L∞P+**. 기존 워드마크와 가상 통신사라는 제품 설정을 유지한다.
- 고객 화면은 “신뢰할 수 있는 국내 통신사의 편리한 고객 포털”, 관리자 화면은 “장시간 사용할 수 있고 이상 징후를 빠르게 파악하는 운영 콘솔”로 개편한다.
- 고객용은 브랜드 표현과 명확한 업무 동선을 결합하고, 관리자용은 스캔 가능한 정보 구조와 상태 인지를 우선한다. 같은 브랜드지만 두 화면의 목적에 맞게 밀도와 강조 수준을 다르게 설계한다.
- 고객 화면에 **가상 통신사 본사 사옥의 외관을 생성한 이미지**를 사용한다. 여기서 “회사 외부 이미지”는 외부 사이트에서 가져온 사진이 아니라 **회사 건물의 외관 이미지**를 뜻한다.
- 사진을 화면 전체 배경으로 깔지 않는다. 사진은 제한된 브랜드 영역에 배치하고 데이터·메뉴·폼·버튼은 읽기 쉬운 단색 면 위에 놓는다.

1. 프로젝트 안의 AGENTS.md 등 적용 지침을 먼저 읽고 `git status --short`와 기존 diff를 확인한다.

3. 프롬프트 작성 시점에는 다음 미커밋 작업이 있었다. 실행 시 다시 확인하고 해당 기능을 보존한다.
   - `backend/app/__init__.py`: Zabbix 라우트 연결 관련 변경

5. 고객/관리자 권한 분리, 로그인·로그아웃, 세션·CSRF, API 요청 본문과 응답 계약, 원래의 업무 동작을 유지한다. 디자인을 위해 인증을 우회하거나 API 주소를 임의로 바꾸지 않는다.
6. `.env`와 비밀값을 출력·복사·문서화하지 않는다. 브라우저에 모니터링 시스템의 인증 토큰을 넣지 않는다.
7. 현재 로컬 파일만 수정한다. `git commit`, `git push`, PR 생성, 컨테이너 이미지 푸시, Kubernetes 적용, 실제 서버 재시작·배포는 하지 않는다. 빌드 검증과 로컬 미리보기는 가능하다.

## 5. 공통 디자인 방향

**핵심 문장: 신뢰감 있는 통신사, 고객에게는 쉬운 업무, 운영자에게는 명료한 상태.**

- 과한 광택, 유리 효과, 무의미한 그라데이션, 네온, 사이버 공격 콘솔 같은 장식은 배제한다.
- 루프 블루는 기본 행동·현재 선택·핵심 강조에 사용한다. 경고와 위험 색을 장식으로 사용하지 않는다.
- 글자는 한글을 오래 읽기 편한 산세리프로 통일한다. 현재 폰트와 시스템 대체 글꼴을 존중하고 대형 폰트 의존성을 불필요하게 추가하지 않는다.
- 타이포그래피·여백·선·정렬·아이콘·버튼·폼 규칙을 토큰과 공통 컴포넌트로 정리한다. 모든 페이지에 서로 다른 스타일을 덧붙이는 방식은 피한다.
- 고객 화면은 가벼운 밝은 바탕, 관리자 화면은 차분한 회백색 또는 채도 낮은 어두운 면으로 장시간 사용을 고려한다. 라이트/다크 모두 대비와 상태 구분을 확인한다. 다크 모드라고 무조건 눈이 덜 피곤하다고 가정하지 않는다.
- 본문은 대체로 15~16px, 표·보조 정보는 읽을 수 있는 크기를 유지한다. 데이터가 많다는 이유로 10~11px 글자를 기본값으로 삼지 않는다.
- 일반 텍스트 대비 4.5:1 이상, 주요 UI 경계·상태 표시 대비 3:1 이상을 목표로 한다. 색상만으로 의미를 전달하지 않는다.
- 숫자·금액·시간·IP·규칙 ID는 정렬과 비교가 쉬워야 한다. 숫자는 tabular-nums, 긴 IP·ID·파일명은 복사/줄바꿈/말줄임·전체 확인 방식을 구분한다.

## 6. 고객 페이지 개편

### 정보 순서

고객은 장식보다 다음 정보를 먼저 찾을 수 있어야 한다.

1. 내 요금제·회선·남은 데이터
2. 이번 달 청구·납부 기한·납부 행동
3. 멤버십 등급·사용 가능한 포인트
4. 자주 쓰는 업무 바로가기
5. 추천 혜택·공지·최근 문의와 결제

현재 고객 홈의 실제 API 값을 재사용하라. 원형 게이지를 유지하거나 더 명료한 요약으로 바꿀 수 있지만, 무제한·회선 없음·미가입·데이터 미수집 상태를 정확히 구분한다.

### 데스크톱 배치

- 상단은 로고, 목적별 주 메뉴, 사용자·테마 메뉴를 안정적으로 배치한다. 메뉴가 애매하게 두 줄로 감겨 사용자 메뉴와 충돌하지 않도록 한다.
- 상단 브랜드 소개는 **좌측 짧은 인사·핵심 행동 / 우측 사옥 이미지** 같은 분할 구성을 우선 검토한다.
- 데스크톱 첫 화면에서 이미지는 소개 영역 가로폭의 약 35~45% 안쪽으로 제한하고, 높이는 대략 260~360px 수준의 출발안으로 조정한다. 100vh 히어로나 화면 전체를 덮는 사진은 금지한다.
- 실제 내 이용현황과 납부 행동이 불필요한 스크롤 뒤로 밀리지 않게 한다. 사진 배치는 사용자 업무 가시성보다 우선하지 않는다.
- 자주 쓰는 업무는 4~6개 정도의 명확한 바로가기 묶음으로 제공하고, 요금 납부·카카오페이처럼 같은 목적지의 버튼은 관계를 분명하게 한다.
- 공지·최근 문의·최근 결제는 제목, 상태, 날짜가 읽히는 목록으로 정리한다. 모든 정보를 같은 크기의 홍보 카드로 만들지 않는다.
- 기존 화면에 없는 요금제 할인, 가입자 수, 전국망 실적, 가동률, 제휴사, 운영 성과를 만들어 넣지 않는다.

### 사옥 이미지 생성

가능한 이미지 생성 도구를 사용해 **허구의 L∞P 본사 외관 이미지**를 실제 자산으로 만든다. 기존 SVG 로고는 코드 자산으로 유지하고 생성 이미지에 로고나 글자를 억지로 그리지 않는다.

생성 지시 예시:

> Photorealistic architectural editorial photograph of a fictional contemporary Korean telecommunications company headquarters, human-scale glass and pale stone facade, subtle deep blue architectural accents, welcoming entrance plaza, a few natural trees, clean daytime light, believable construction details, modest modern corporate campus, eye-level three-quarter view, calm professional atmosphere, wide horizontal composition, no readable signs, no logos, no text, no giant antenna towers, no neon, no sci-fi city, no server-room imagery. This is a fictional company building, not an existing company's headquarters.

- 저장 위치 예시: `frontend/public/images/brand/loop-headquarters.png`. 변환 도구가 있으면 최적화된 WebP/AVIF와 필요 대체 파일을 사용한다.
- 생성 원문 프롬프트와 실제 자산 경로를 문서에 남긴다. 생성 사진을 실제 회사 소유 건물의 사진으로 주장하지 않는다.
- 이미지 위에 작은 본문이나 필수 조작을 겹치지 않는다. 정보는 별도 HTML 텍스트로 제공한다.
- `object-fit`, `object-position`, 명시적인 크기·비율을 지정해 잘림과 레이아웃 흔들림을 방지한다.
- 모바일에서는 짧은 이미지 영역으로 축소하거나 본문 아래로 이동한다. 이미지 때문에 데이터·청구 요약이 첫 화면에서 사라지지 않게 한다.
- 같은 사옥 사진을 모든 업무 화면에 반복하지 않는다. 고객 홈·로그인 등 브랜드 소개가 필요한 위치에만 제한적으로 사용한다.
- 생성 도구가 없다면 이미지가 완성됐다고 주장하지 않는다. 나머지 UI를 진행하고 필요한 자산과 미완료 사유를 명확히 남긴다. 존재하지 않는 이미지 경로나 임의의 사진 주소를 최종 결과로 남기지 않는다.

### 로그인·업무 화면

- 로그인·회원가입은 폼이 주인공이다. 데스크톱은 소개 영역과 폼을 나눌 수 있으나 모바일은 폼을 먼저 보여준다.
- 이용현황·요금제·결제·멤버십·상점·공지·문의·설정에 공통 컴포넌트와 디자인 규칙을 적용한다.
- 납부·구매·문의 접수 같은 핵심 행동은 명확하고, 중복 제출 방지·진행 중·완료·실패 안내를 보존한다.
- 기존의 가상 통신사·실습 결제 안내는 지우지 않는다.

## 7. 관리자 페이지 개편

### 오래 보는 화면의 원칙

- 사진·홍보 배너·움직이는 배경을 넣지 않는다. 낮은 채도의 중립 배경, 구분 가능한 패널, 안정적인 글자 대비를 사용한다.
- 초대형 숫자 카드만 반복하지 말고 **무엇이 이상인지 → 어느 대상인지 → 언제부터인지 → 무엇을 할지**가 이어지게 배치한다.
- 기본 레이아웃은 **고정된 주 탐색 영역 + 상단 페이지 도구 + 본문 업무 영역**을 권장한다. 사이드바가 적합하면 기존 메뉴를 운영 업무/보안 관리/관제 도구로 묶고 현재 위치를 명확히 표시한다. 긴급 메뉴를 여러 단계 드롭다운 안에 숨기지 않는다.
- 최대 폭은 고객 화면보다 넓게 쓰되 정보의 읽기 순서를 유지한다. 표는 폭에 맞게 열 우선순위를 정하고 세부 정보는 상세 화면으로 연결한다.

### 대시보드 정보 계층

**A. 상단: 현재 확인해야 할 상태**

- 기존 API가 제공하는 실제 긴급·높음 인시던트, 권한 정책 위반, Zabbix DOWN/활성 장애 등을 우선 배치한다.
- 경보 수, 영향 대상, 관련 화면 이동을 제공한다. 조회 실패와 데이터 없음은 정상으로 계산하지 않는다.
- 확인되지 않은 가동률이나 전체 시스템 정상 여부를 합성하지 않는다. 실제 API가 없으면 해당 항목을 “미연결” 또는 “확인 불가”로 표현한다.

**B. 다음: 바로 처리할 업무**

- 미해결 인시던트, 답변 대기 문의, 차단 IP, 잠긴 계정, 권한 위반 등 기존 수치를 적절히 그룹화한다.
- 모든 수치 타일을 빨간색으로 만들지 않는다. 차단 IP나 잠긴 계정이 있다는 사실은 대응 상태일 수도 있으므로 “새로운 위험”과 구분한다.
- 클릭하면 실제 관련 상세/목록 화면으로 이동한다. API가 제공하지 않는 심각도 필터를 URL에 붙여 동작하는 것처럼 꾸미지 않는다.

**C. 중간: 운영 상황과 관제**

- 인시던트 심각도와 처리 대기 목록을 읽기 쉬운 구조로 배치한다.
- 기존 Grafana 임베드, Zabbix 패널, 관제 도구 링크를 보존한다. 사용자 미커밋 Zabbix 작업을 제거하거나 이전 버전으로 되돌리지 않는다.
- Zabbix의 서비스 상태, CPU/RAM/디스크/RX/TX, 활성 장애를 일관된 단위·시각·우선순위로 보여준다. 단순 TCP 확인을 전체 서비스 정상으로 표시하지 않는다.
- CPU/RAM/디스크/RX/TX의 단위와 측정 대상 PC를 보존한다. 수치 크기만으로 근거 없는 장애 기준을 새로 만들지 않는다.
- 기존 30초 갱신을 보존하되 갱신 때 패널 전체가 깜빡이거나 사용자가 입력한 필터·스크롤이 초기화되지 않게 한다. 타이머 중복·요청 경합도 확인한다.
- Grafana 로딩/미설정/접근 실패를 다른 정상 데이터와 구분한다. iframe 내부를 제어할 수 없으면 주변 프레임과 테마만 맞추고 내부 색상까지 변경됐다고 주장하지 않는다.

**D. 하단: 업무 통계와 관련 도구**

- 활성 고객·신규 고객·미납 청구·기타 업무 통계를 정돈한다.
- 관제 도구 링크는 실제 설정된 주소만 연결한다. 주소 미설정 항목은 비활성 안내로 표현한다.

### 상태 의미와 시각 표현

- `정상`, `주의`, `위험`, `미연결`, `수집 대기`, `조회 실패`, `오래된 데이터`를 텍스트·아이콘·색으로 구분한다.
- “경보 없음”, “응답이 비어 있음”, “연결 실패”를 같은 상태로 표시하지 않는다.
- 마지막 측정 시각, 마지막 조회 시각, 화면 렌더 시각을 구분한다. `new Date()`로 만든 화면 시각을 실제 측정 시각이라고 표시하지 않는다.
- 시간은 기존 한국어 표시·Asia/Seoul 의미를 유지하고, 실제 측정 시각이 없으면 없다고 표시한다.
- Wazuh/Graylog는 현재 데이터 API가 있는지 먼저 확인한다. 링크만 있는데 경보 목록·에이전트 온라인 상태가 실시간으로 조회되는 것처럼 만들지 않는다. 이번 디자인 작업에서 새 백엔드 연동을 임의로 구현하지 않는다.
- 자동조치는 “판정”, “요청”, “API 처리 결과”, “실제 적용 확인”을 구분한다. HTTP 2xx만 보고 실제 방화벽 차단·계정 잠금까지 검증됐다고 표시하지 않는다.
- 삭제·차단 해제·계정 잠금·권한 회수 같은 중요한 조작의 기존 확인 절차를 유지한다. 새로고침이나 정렬 조작과 위험 행동을 시각적으로 분리한다.

## 8. 접근성·반응형·품질 기준

- 대표 너비 1440px, 1024px, 768px, 390px에서 확인한다. 360px에서도 본문 전체의 가로 스크롤이 생기지 않게 한다. 넓은 데이터 표의 제한된 내부 스크롤은 명확한 경계를 제공한다.
- 고객 화면은 모바일에서도 요금·이용량·주요 업무를 쉽게 찾을 수 있어야 한다. 관리자 화면은 모바일에서 핵심 상태→주요 목록→상세 순서를 보존한다.
- 메뉴는 키보드로 이동·열기·닫기가 가능해야 한다. 기존 Esc·바깥 클릭 동작을 보존하고 포커스 표시와 포커스 복귀를 확인한다.
- 터치 대상은 기본 44px 수준의 조작 면적을 확보하고, 표의 작은 조작은 충분한 간격을 둔다.
- 상태는 색만으로 구분하지 않는다. 폼에는 실제 label, 오류 설명, loading/disabled 상태가 있어야 한다.
- 이미지에는 역할에 맞는 alt를 제공한다. 장식 이미지는 빈 alt를 쓰고 동일 설명을 중복 낭독시키지 않는다.
- hover만으로 열리는 필수 메뉴, 자동 넘김 배너, 지속 깜빡임, 과도한 스크롤 애니메이션을 사용하지 않는다. reduced-motion을 존중한다.
- CSS 전체 파일 끝에 임시 덮어쓰기를 계속 쌓지 말고, 기존 토큰과 중복 선언을 읽고 컴포넌트 범위에 맞게 정리한다. 고객·관리자 테마가 서로 오염되지 않도록 한다.
- 필요 없는 UI 프레임워크나 차트 라이브러리를 새로 도입하지 않는다. 기존 React/CSS와 가벼운 SVG로 해결 가능한 부분을 우선한다.
- 레이아웃 안정성을 위해 이미지 크기를 예약하고, 정보 갱신 중에도 기존 표시값과 레이아웃을 안정적으로 유지한다.

## 9. 구현·검증 순서

1. 기존 변경과 구조·라우트를 확인하고, 현재 고객/관리자 대표 화면을 살펴본다.
2. 참고 사이트에서 구조 원칙을 추출하고, 이번 요청에 맞는 하나의 일관된 방향을 잡는다. 일반적인 세부 선택은 스스로 결정해 진행한다.
3. 고객/관리자 공통 토큰과 컴포넌트 경계를 정리한다.
4. 사옥 이미지를 생성·저장하고 제한된 고객 브랜드 영역에 연결한다.
5. CustomerLayout·고객 홈·로그인·고객 업무 화면을 정리한다.
6. AdminLayout·관리자 대시보드·표·상태·관제 패널을 정리한다. 기존 사용자 변경과 연동을 보존한다.
7. `frontend`에서 `npm run typecheck`, `npm run build`를 실행한다. 기존 오류가 있다면 새 변경으로 생긴 오류와 구분한다. 단순 스타일 변경을 위해 백엔드 시험을 무분별하게 확대하지 않는다.
8. 로컬 미리보기에서 데스크톱과 모바일 대표 화면을 한 번에 점검하고 발견된 문제를 일괄 수정한 뒤 한 번 더 확인한다. 끝없는 미세 수정이나 반복 촬영을 하지 않는다.
9. 고객은 로그인·이용현황·납부·멤버십·문의, 관리자는 메뉴 이동·인시던트·IP 차단·자동화·Grafana·Zabbix 상태를 검증한다. 디자인 확인을 위해 실제 결제·계정 잠금·권한 회수·인시던트 삭제를 실행하지 않는다.
10. 인증/백엔드 연결이 없어 실데이터 화면을 열 수 없다면 보호 로직을 제거하지 않는다. 개발용 미리보기나 테스트 픽스처는 운영 경로에 섞지 않고, 실데이터·권한·연동이 검증되지 않은 부분을 명확히 보고한다.

## 10. 완료 조건과 결과 보고

다음을 충족해야 완료다.

- 통신사 브랜드가 고객 화면의 타이포그래피·색·이미지·업무 구조에서 일관되게 드러난다.
- 생성한 사옥 이미지가 실제 파일로 연결돼 있고 전체 화면 배경을 덮지 않는다.
- 고객의 이용량·청구·납부·멤버십 동선이 사진보다 우선하며 모바일에서도 쉽게 찾을 수 있다.
- 관리자는 높은 위험·업무 대기·관제 연결 실패를 구분해서 볼 수 있다. 중요 정보가 첫 화면의 장식에 밀리지 않는다.
- 현재 Zabbix 연결과 Grafana·모니터링 링크를 보존하며 데이터가 없는 상태를 정상으로 표시하지 않는다.
- 라이트/다크, 키보드 탐색, 폼·표·메뉴·상태 표현이 일관된다.
- 원래 API 계약·인증·업무 동작을 보존하고, 사용자 미커밋 변경을 덮어쓰지 않았다.
- 빌드·타입 검사 결과와 대표 화면 확인 결과가 기록돼 있다.
- 커밋·푸시·PR 생성·실제 배포를 하지 않았다.

최종 답변에는 다음만 간결하게 보고하라.

1. 고객 화면과 관리자 화면에서 각각 무엇을 바꿨는지
2. 수정 파일과 생성한 이미지 경로
3. 참고한 사이트와 적용한 구조 원칙
4. 타입 검사·빌드·화면 검증 결과
5. 백엔드/API 부재 등으로 실제 검증하지 못한 부분
6. 커밋·푸시·배포 없이 로컬 파일만 수정했다는 사실
