# LOOP 결과보고서 발표 대본 — 문경구

기준 PPT: `LOOP_결과보고서_인프라검증완성_2026-11-04.pptx` · 총 39장

기존 역할별 대본에서 문경구 담당 내용만 다듬고, 새로 추가한 검증·시연 페이지에 맞춰 작성했습니다. 다른 조원의 발표 내용은 수정하지 않았습니다. 아래 **발표 대본**은 그대로 읽고, 대괄호로 쓴 진행 안내는 읽지 않습니다. 숫자는 해당 캡처와 시험에서 확인한 결과를 뜻합니다.

관리자 접속 설명은 2026-11-04 병합된 PR #63 정책을 반영했습니다. 공개 고객 주소의 관리자 UI/API는 404로 차단하며, 관리자 업무는 허용된 관리 전용 입구에서 인증합니다. PPT에 남은 과거 공개 관리자 401·접근 허용 설명은 현재 정책으로 교정한 뒤 발표합니다.

## 1쪽. 표지

**발표 대본**

안녕하세요. 가상 통신사 웹 서비스와 보안 관제 환경을 구축한 LOOP 팀입니다.

저희는 고객과 관리자가 사용하는 웹 서비스를 만들고, 이를 실제 학원망에 배포했습니다. 여기에 보안 이벤트 수집과 알림, 웹 서버 장애 대응, 데이터베이스 복제와 백업·복원까지 연결했습니다.

오늘은 각 담당자가 구축한 내용과 실제 시험 결과를 순서대로 설명드리겠습니다.

## 2쪽. 목차

**발표 대본**

먼저 프로젝트의 목표와 전체 시스템 구성을 소개하겠습니다. 이어서 고객·관리자 웹 기능과 관제 연동을 설명하고, 웹 이중화와 데이터 보호 기능을 영상과 검증 화면으로 보여드리겠습니다.

그다음 공격 시연과 정적분석 내용을 살펴보고, 마지막으로 구현 결과와 개선 과제를 정리하겠습니다.

## 3쪽. 프로젝트 개요

**발표 대본**

LOOP는 학원망 안에 구축한 가상 통신사 서비스입니다. 실제 고객의 개인정보나 결제 정보를 사용하는 환경은 아닙니다.

React로 고객·관리자 화면을 만들고, Flask API가 업무 요청을 처리하도록 구성했습니다. 웹과 API는 두 대의 Ubuntu VM에 배포했습니다.

운영 과정에서 발생하는 보안 이벤트와 자원 상태도 함께 확인할 수 있도록 관제 시스템을 연결했습니다. 데이터는 현재 PC2의 MySQL에서 처리하고 PC1으로 복제합니다.

## 4쪽. 선정 배경 및 목표

**발표 대본**

프로젝트를 진행하면서 웹 기능이 동작하는 것뿐 아니라, 장애나 보안 문제가 발생했을 때 어떻게 대응할지도 확인하고 싶었습니다.

그래서 고객과 관리자의 접근 권한을 구분하고, 한쪽 웹 VM이 중단되면 다른 노드가 요청을 처리하도록 구성했습니다. 보안 이벤트는 담당자가 확인할 수 있도록 웹 인시던트와 Discord 알림으로 연결했습니다.

데이터 보호에서는 복제와 백업을 따로 준비했습니다. 복제본에도 잘못된 변경이 전달될 수 있기 때문에, 별도 백업으로 복원할 수 있는지도 시험했습니다.

## 5쪽. 역할 분담

**발표 대본**

팀은 네 분야로 역할을 나눴습니다.

김준식 님은 고객·관리자 웹과 업무 API, 데이터 모델을 담당했습니다. 저는 Docker와 k3s 배포, HAProxy 연동, DB 역할 전환과 복제, 백업·복원 검증을 담당했습니다.

정동석 님은 pfSense 접속 정책과 Suricata를, 김준오 님은 Wazuh·Graylog·Zabbix와 n8n·Discord 연동을 담당했습니다.

HTTPS와 배포, 관제 연결처럼 여러 영역에 걸친 작업은 담당자들이 함께 확인했습니다.

## 6쪽. 주요 추진 일정

**발표 대본**

10월 하순에는 웹 이미지와 k3s 배포, DB 복제·백업의 기본 구성을 먼저 만들었습니다.

이후 공통 HTTPS 주소와 네트워크 접근 정책을 정리했고, PC2를 DB 쓰기 서버로 전환한 뒤 PC1이 복제본을 유지하도록 구성했습니다.

웹 VM 중단 시험에서는 처음에 응답 오류가 발생해 연결 경로와 HAProxy 상태 검사를 조정했습니다. 11월 초에는 새 코드 배포와 관리자 경로, 백업·복원 결과를 확인했고, 현재는 최종 시연과 보고서 정리를 진행하고 있습니다.

## 7쪽. 사용 기술 및 선정 이유

**발표 대본**

각 기술은 서비스에서 맡는 역할을 기준으로 선택했습니다.

React와 Flask가 화면과 업무 처리를 담당하고, Nginx가 HTTPS 요청과 API 전달을 처리합니다. Docker 이미지와 k3s는 두 VM에 같은 실행 환경을 배포하는 데 사용했습니다.

pfSense와 HAProxy는 접속 정책과 연결 분산을 담당합니다. Wazuh와 Graylog는 보안 이벤트를, Zabbix는 운영 상태를 확인하고, n8n은 웹 기록과 Discord 알림을 연결합니다.

이 도구들이 실제로 어떻게 연결되는지 다음 구성도에서 설명드리겠습니다.

## 8쪽. 전체 네트워크 구성도

[화면: 사용자, PC3, 두 Ubuntu VM, DB 복제 방향 순서로 가리킵니다.]

**발표 대본**

사용자는 학원망에서 공통 주소인 192.168.3.30으로 접속합니다. 이 주소로 들어온 웹 요청은 PC3의 pfSense와 HAProxy를 거쳐 PC1 또는 PC2의 Ubuntu VM으로 전달됩니다.

두 VM 모두 웹과 API를 실행합니다. 데이터베이스는 Windows의 Docker에서 실행하며, PC2가 현재 Primary, PC1이 Replica입니다.

관제 도구는 PC1과 PC2에 나눠 배치했습니다. 현재 구성은 학원의 기존 네트워크를 사용하며, 프로젝트용 VLAN이나 Keepalived는 적용하지 않았습니다. 구성도에 표시한 것은 공통 웹 주소의 접속 경로입니다.

## 9쪽. 서비스 아키텍처

**발표 대본**

실제 요청 흐름을 조금 더 자세히 보겠습니다.

사용자의 HTTPS 연결을 HAProxy가 웹 노드의 30443 포트로 전달하고, 해당 노드의 Nginx Edge가 요청을 받습니다. 화면 요청은 같은 노드의 Web 서비스로, API 요청은 같은 노드의 API 서비스로 보냅니다.

이렇게 경로를 나눈 이유는 한쪽 VM이 중단됐을 때 살아 있는 노드가 중단된 노드의 API를 다시 선택하는 문제를 줄이기 위해서입니다.

두 API의 업무 데이터 읽기와 쓰기는 PC2 MySQL이 처리합니다. 사용자 브라우저가 DB에 직접 접속하는 구조는 아닙니다.

## 10쪽. Kubernetes 배포 구조

[화면: 두 노드의 Ready와 실행본 배치 캡처를 가리킵니다.]

**발표 대본**

k3s 클러스터는 하나입니다. PC1은 클러스터를 관리하는 서버이면서 Worker이고, PC2는 Agent이면서 Worker입니다.

Web과 API, Edge를 두 노드에 각각 배치했고, 이름을 찾아주는 CoreDNS도 두 노드로 분산했습니다. 화면에서는 두 노드가 Ready이고 주요 Deployment의 실행본이 두 개씩 준비된 것을 확인할 수 있습니다.

다만 클러스터 제어부는 PC1 한 대에 있습니다. PC1이 중단돼도 PC2의 기존 실행본이 서비스를 처리할 수 있지만, 그동안 클러스터의 배포 관리나 자동 재배치를 정상적으로 수행할 수 있는 구성은 아닙니다.

## 11쪽. HTTPS와 접근 정책

**발표 대본**

웹 접속은 HTTP에서 HTTPS로 이동하도록 설정했습니다. HAProxy는 사용자의 TLS 연결을 웹 노드까지 전달하고, Nginx가 이를 처리합니다. 상태 검사에도 HTTPS와 프로젝트 CA를 사용합니다.

DB의 3306 포트는 필요한 API와 복제 연결만 허용했습니다. 공개 웹 주소에서는 내부 자동화 API를 차단하고, 자동화 담당 PC는 별도 접속 경로와 토큰을 사용합니다.

11월 4일 변경한 정책에 따라 공개 고객 주소의 관리자 화면과 API도 404로 차단합니다. 관리자 업무는 허용된 관리 전용 주소로 접속하며, 그 안에서도 Flask가 로그인 세션과 ADMIN 역할을 검사합니다. 네트워크 접근 허용과 관리자 계정 권한을 함께 확인하는 방식입니다.

여기까지 인프라와 접속 구조를 설명드렸습니다. 이어서 김준식 님이 웹 기능을 소개하겠습니다.

## 18쪽. 웹 이중 배치와 연결 분산

**발표 대본**

이어서 웹 이중화와 데이터 보호 결과를 설명드리겠습니다.

웹은 두 노드가 함께 요청을 처리하도록 구성했습니다. HAProxy의 Round Robin 방식으로 새 연결을 나누고, 각 노드의 Edge는 같은 노드에 있는 Web과 API를 사용합니다.

상태 검사는 API의 준비 상태와 DB 연결까지 확인합니다. 검사에 실패한 노드는 새 연결 대상에서 제외하고, 복구하면 다시 포함합니다.

이 구성으로 PC1 Ubuntu VM 중단 시험을 진행했습니다. 구체적인 동작은 뒤의 영상과 응답 기록에서 보여드리겠습니다.

## 19쪽. DB 역할 전환 및 복제

[화면: PC2의 2·0·0과 PC1의 1·1·1을 짚습니다.]

**발표 대본**

웹은 두 노드에서 함께 처리하지만, DB 쓰기 대상은 PC2 한 곳으로 정했습니다.

PC2는 서버 ID가 2이고 읽기 전용 설정이 꺼져 있어 업무 읽기와 쓰기를 처리합니다. PC1은 서버 ID가 1이고 두 읽기 전용 설정을 켜서 복제본으로 운영합니다.

초기 PC1 Primary 구성을 수동으로 전환한 뒤, 현재는 PC2에서 PC1으로 데이터를 복제합니다. 두 API의 접속 대상도 PC2와 업무용 webuser 계정으로 확인했습니다.

DB 자동 승격은 아직 구현하지 않았으므로, 웹의 자동 연결 전환과 DB 역할 전환은 구분해서 보시면 됩니다.

## 20쪽. 예약 백업·격리 복원·실패 알림

**발표 대본**

PC2 Primary에서는 한 시간 간격으로 예약 백업을 실행합니다. 백업 파일과 해시, 실행 결과를 기록하고, 파일이 실제로 복원되는지도 별도로 검사했습니다.

선택한 백업을 시험용 MySQL 컨테이너에 복원했을 때 26개 테이블 검사가 정상으로 끝났습니다.

백업 실패 감시도 함께 구성했습니다. 의도적으로 실패를 발생시킨 뒤 Discord의 실패 알림을 확인했고, 정상 백업을 다시 실행한 후 복구 알림까지 확인했습니다. 세부 검증 화면은 뒤에서 이어서 보여드리겠습니다.

## 21쪽. 배포 및 환경 설정 관리

**발표 대본**

배포할 때는 GitHub에 코드가 올라간 상태와 실제 서비스에 반영된 상태를 따로 확인했습니다.

프론트엔드와 백엔드 이미지를 빌드해 두 VM에 전달하고, 소스 커밋과 이미지 태그, 아카이브 해시를 대조했습니다. 이후 실행 중인 Pod의 이미지와 DB 접속 대상도 확인했습니다.

환경 파일은 이미지에 포함하지 않고 Kubernetes Secret으로 전달했습니다. 환경 설정을 바꾼 뒤에는 실행 중인 Pod가 새 설정을 사용하는지 다시 검사했습니다. 현재 배포 절차는 공개 관리자 404 정책도 함께 검사합니다. 오늘 병합된 새 도구의 양 노드 재배포 결과는 별도 확인 항목으로 남겼습니다.

이제 이 배포 환경에서 연결 분산이 동작하는 영상을 보겠습니다.

## 23쪽. 웹 이중화 메인 서버 중단 시연

[영상 재생 전]

**발표 대본**

두 번째 영상에서는 PC1 Ubuntu VM을 중단하고, PC2가 서비스를 계속 처리하는지 확인합니다.

확인할 부분은 PC1 중단 이후 HAProxy의 PC1 상태가 DOWN으로 바뀌는지, PC2는 UP을 유지하는지, 그리고 공통 주소의 웹과 API가 응답하는지입니다.

이 시험에서는 PC2의 DB를 계속 가동합니다. PC1 Windows 전체의 전원을 끄는 시험과는 범위가 다릅니다.

[영상 재생. VM 중단, HAProxy 상태 변경, 웹 응답 장면을 차례로 보여줍니다.]

[영상 종료 후]

**발표 대본**

PC1 VM이 중단된 동안 PC2 경로로 서비스가 응답하는 모습을 확인했습니다. 이어서 같은 시험의 요청 결과를 보겠습니다.

## 24쪽. 웹 노드 중단 시험 결과

[화면: API 112건과 웹 112건의 집계, 실패 목록이 없는 결과를 가리킵니다.]

**발표 대본**

VM 중단 시험에서 API 준비 상태 경로와 웹 첫 화면을 반복 요청했습니다.

기록된 결과는 API 112건, 웹 112건으로 총 224건입니다. 모두 HTTP 200과 curl 종료 코드 0을 확인했습니다.

따라서 이 시험 구간에서는 요청 실패를 관측하지 않았습니다. 다만 이 결과만으로 모든 장애에서 무중단이 보장되거나, 이미 열린 연결까지 다른 서버로 그대로 이동한다고 설명할 수는 없습니다.

## 25쪽. VM 중단과 운영 상태 확인

[화면: CPU 기록, PC1 OFF·PC2 ON, HAProxy DOWN·UP 순서로 가리킵니다.]

**발표 대본**

시연에서는 CPU 사용률이 90퍼센트를 넘으면 VM 종료를 실행하도록 조건을 설정했습니다. 왼쪽 기록에서 임계값 초과를 확인하고, 운영 화면과 HAProxy에서 상태 변화를 함께 확인했습니다.

CPU가 90퍼센트를 넘으면 서버가 원래 자동으로 꺼지는 것은 아닙니다. 장애 상황을 재현하기 위해 저희가 설정한 시연용 동작입니다.

또 운영 화면의 OFF는 Ping이나 SSH 같은 연결 응답을 확인한 결과입니다. VM의 전원 상태를 직접 측정한 값과는 구분해서 해석했습니다.

## 26쪽. DB 복제와 암호화 검증

[화면: IO·SQL Yes, 지연 0, 오류 0, 서버 인증서 검증 Yes를 짚습니다.]

**발표 대본**

DB에서는 PC2의 변경 내용을 PC1이 정상적으로 받아 적용하는지 확인했습니다.

PC1의 복제 상태에서 IO와 SQL 실행이 모두 Yes이고, 확인 시점의 지연과 오류가 0인 것을 볼 수 있습니다. 복제 연결에는 TLS를 적용하고 서버 인증서 검증도 켰습니다.

GTID는 처리한 변경 내역을 식별하는 값입니다. PC2에서 확인한 체크포인트를 PC1이 적용할 때까지 기다리는 검사에서 결과 0을 확인했습니다. 이는 선택한 지점까지 적용됐다는 의미입니다.

이 복제 상태와 별도로, 삭제나 잘못된 변경을 복구하기 위한 백업도 검증했습니다.

## 27쪽. 백업 파일의 격리 복원 검증

[화면: 26 tables CHECK TABLE OK와 restore-verified를 가리킵니다.]

**발표 대본**

백업 검증에서는 파일이 만들어졌는지에서 끝내지 않고, 실제로 열어 사용할 수 있는지 확인했습니다.

선택한 PC2 Primary 백업을 별도 시험 MySQL 컨테이너에 복원했습니다. 그 결과 26개 테이블의 CHECK TABLE 검사가 정상으로 끝났고, 행 수 기록과 restore-verified 상태를 확인했습니다.

시험은 운영 DB와 분리해서 진행했으며 운영 DB와 원본 볼륨은 유지했습니다. 이 화면은 선택한 백업의 복원 검증 결과입니다.

## 28쪽. 백업 실패 감시와 복구 확인

[화면: 실패 전달, 같은 상태 재검사, 정상 복구의 세 캡처를 순서대로 가리킵니다.]

**발표 대본**

마지막으로 백업이 실패했을 때 운영자가 이를 알 수 있는지 시험했습니다.

인증 파일을 일시적으로 사용할 수 없게 해 백업 실패를 발생시켰고, 감시 도구에서 알림 전달 확인 상태를 확인했습니다. 같은 실패 상태를 다시 검사했을 때는 이미 알린 내용이라 추가 전송을 생략했습니다.

이후 인증 파일을 복구하고 예약 백업을 다시 실행했습니다. 새 백업 성공과 healthy 상태를 확인했으며, 앞쪽 Discord 캡처에서는 실패와 정상 복구 메시지의 실제 수신도 확인할 수 있습니다.

반복 알림을 줄이면서 실패와 복구를 모두 알리는 흐름까지 검증했습니다.

## 29쪽. 현재 이중화 범위와 운영 한계

**발표 대본**

여기까지 확인한 범위를 정리하겠습니다.

웹은 두 노드가 함께 요청을 처리하고, HAProxy가 상태 검사에 실패한 노드를 제외합니다. DB는 PC2 한 곳에서 쓰기를 처리하고 PC1이 복제본을 유지합니다. 백업은 예약 실행과 격리 복원, 실패·복구 알림까지 확인했습니다.

남은 한계도 있습니다. PC1은 단일 Control Plane이고 PC3도 단일 접속 장비입니다. DB 역할 전환은 수동이며, 백업을 장비 밖에 보관하는 체계도 보완해야 합니다.

따라서 현재 성과는 웹 실행 계층의 분산과 VM 중단 시 서비스 응답, 그리고 DB 복제·복구 절차의 검증입니다.

이상으로 인프라와 데이터 보호 설명을 마치겠습니다. 이어서 정동석 님이 공격 시연과 분석 내용을 설명하겠습니다.

## 발표 전 확인 메모

- 22·23쪽은 PowerPoint 슬라이드 쇼에서 실제 영상 재생과 소리를 먼저 확인합니다. 영상 중에는 확인 지점만 짧게 말하고, 화면을 볼 시간을 둡니다.
- HAProxy 통계가 보여주는 것은 연결 분산입니다. 두 서버가 모든 HTTP 요청을 정확히 절반씩 처리한다고 설명하지 않습니다.
- 웹의 두 노드는 함께 처리하지만, 현재 DB 쓰기 서버는 PC2 한 곳입니다. ‘PC1 메인’이라는 표현은 영상 속 중단 대상과 혼동될 수 있으므로 ‘PC1 Ubuntu VM’으로 말합니다.
- 224건 응답, CPU 임계값 시연, 복원 결과는 각각의 캡처와 시험에 대한 근거입니다. 별도 시험의 수치나 시각을 하나의 연속 측정처럼 설명하지 않습니다.
- 26개 테이블 복원에 사용한 백업과, 실패 시험 이후 새로 성공한 백업은 서로 다른 실행입니다. 새 백업까지 다시 복원했다고 덧붙이지 않습니다.
- 다른 담당자의 대본은 그대로 사용하되, 공격·분석 구간은 기존 22~27쪽에서 현재 30~35쪽으로, 종합·마무리는 기존 28~31쪽에서 현재 36~39쪽으로 이동했습니다.
- 관리자 접근 정책은 [11월 4일 변경 기록](../operations/2026-11-04-public-admin-guard.md)을 따릅니다. 과거 공개 관리자 401은 당시 결과이고, 현재 공개 입구의 기대값은 404입니다. 관리 전용 입구는 `https://192.168.7.178:9443/admin`이며 허용 PC 정책과 ADMIN 인증을 함께 적용합니다. 이 상대 링크는 저장소 `docs/presentations/`에 게시한 대본 기준입니다.

## 질문을 받았을 때 짧게 답할 내용

**PC1이 꺼져도 모든 기능이 완벽하게 유지되나요?**

PC1 Ubuntu VM 중단 시험에서는 PC2의 기존 웹·API와 PC2 DB를 통해 서비스 응답을 확인했습니다. PC1의 단일 제어부와 PC1에 있는 Graylog까지 이중화한 것은 아니므로, 전체 시스템의 모든 기능이 유지된다고 설명하지는 않습니다.

**PC2 DB가 꺼지면 PC1 DB가 자동으로 대신하나요?**

현재는 자동 전환하지 않습니다. 쓰기 서버를 확실히 격리하고 복제 상태를 확인한 뒤 DB 역할과 API 접속 대상을 수동으로 전환하는 절차가 필요합니다.

**복제본이 있는데 백업도 필요한 이유는 무엇인가요?**

잘못된 삭제나 변경도 복제본에 전달될 수 있습니다. 이전 시점의 데이터를 복구하기 위해 별도 백업이 필요하고, 저희는 선택한 백업을 격리된 MySQL에 복원해 검사했습니다.

**CPU가 높아지면 운영 서버도 자동으로 종료하나요?**

이번 종료 동작은 장애 전환을 보여주기 위해 설정한 시연 조건입니다. CPU 사용률만으로 운영 서버를 종료하는 정책을 일반적인 운영 방식으로 제안한 것은 아닙니다.

**HTTPS를 사용하면 Suricata가 요청 본문까지 모두 볼 수 있나요?**

현재 HAProxy는 사용자의 TLS 연결을 웹 노드까지 통과시킵니다. 별도 복호화 구성이 확인되지 않은 상태에서 Suricata가 암호화된 웹 본문까지 분석한다고 설명할 수는 없습니다.
