## 2. Graylog → n8n → 웹 API 연동 점검

### 테스트 자료 재정리

- 기존 Graylog 이벤트 정의별 테스트 21종을 ZIP으로 다시 제공했다.
- 압축 파일: `C:\gov\SKT aleph\Graylog_n8n_항목별_테스트.zip`
- 각 항목은 `test.py`와 `실행명령어.txt`로 구성되며, 공통 `_common.py`가 포함된 전체 `test` 폴더를 유지해야 한다.
- 기본 로그 전송 대상은 PC1 Graylog의 `192.168.3.18:12201/UDP`이다.
- SQL Injection 의심 경보와 404 폭주 자동 IP 차단 테스트 명령을 안내했다. 합성 로그 전송과 실제 공격 실행을 구분했고, 자동조치 경로는 실제 웹 API를 호출할 수 있음을 명시했다.

### HTTPS 인증서 문제

- n8n의 `unable to verify the first certificate` 오류를 확인했다.
- 서버에서 `/home/loop/telecom-https.DcJcRv/lab-ca.crt`를 찾았다.
- 인증서 이름은 `Telecom Lab Root CA`이며, CA 인증서로 정상 해석되고 당시 유효기간 안에 있음을 확인했다.
- PC2에 공개 CA 인증서를 `C:\Users\user\Downloads\telecom-lab-ca.crt`로 저장하도록 안내했다. 개인키는 복사하지 않았다.
- Windows curl의 폐기 상태 확인 오류는 진단용 `--ssl-revoke-best-effort` 옵션으로 구분했다. 이 옵션은 인증서 전체 검증을 끄는 `--insecure`와 다르다.
- curl 출력에서 서버 인증서의 IP가 `192.168.3.30`과 일치함을 확인했다.
- Docker의 `n8n` 컨테이너에 `/opt/custom-certificates/telecom-lab-ca.crt`로 CA를 복사하고 권한 설정 후 재시작하는 방법을 안내했다.
- 이후 n8n이 인증서 오류 대신 웹 API 응답을 받는 상태로 진행됐다.

### Nginx 502 및 API Pod 복구

| 대상 포트 | 당시 결과 | 판단 |
|---|---|---|
| 10443 | 502 | 자동화 Nginx에서 API로 연결 실패 |
| 443 | 404 | 해당 진입점에서 내부 API 경로를 제공하지 않음 |
| 11443 | 404 | 해당 진입점에서 내부 API 경로를 제공하지 않음 |
| 8444 | 시간 초과 | 해당 IP·포트로 연결 실패 |

- 자동화 Nginx의 전달 대상이 `http://telecom-api:5000`임을 실제 설정에서 확인했다.
- Kubernetes Service `telecom-api`는 존재했지만 Deployment가 `0/0`이고 EndpointSlice의 연결 대상이 비어 있었다.
- 오류 로그는 `connect() failed (111: Connection refused)`였다.
- 기존 Kubernetes API를 사용하는 경우에 한해 Deployment의 실행 개수를 1로 올리는 명령을 안내했고, 사용자가 실행 완료를 알렸다.
- 이후 `https://192.168.3.30:10443/api/internal/incident-events`에 토큰 없는 요청을 보내 `401 UNAUTHORIZED`를 확인했다. API까지 도착했음을 확인한 것으로, DB 저장 성공 판정은 아니다.

### DB 읽기 전용 오류

- 인증된 n8n 요청에서 `503 DB_UNAVAILABLE`가 발생했다.
- 상세 로그의 실제 원인은 MySQL 오류 1290, `--read-only` 설정에 따른 인시던트 INSERT 거부였다.
- DB 연결 실패·파일 권한·n8n 권한 부족과 구분하고, API가 쓰기 가능한 주 DB를 사용하는지 확인하도록 안내했다.
- DB 계정의 권한을 무조건 높이거나 복제 DB의 읽기 전용을 바로 해제하지 않도록 설명했다.
- 사용자가 최종적으로 전체 연동이 정상 작동한다고 보고했다. 전체 연동 성공은 사용자 확인에 근거하며, 에이전트가 직접 모든 단계를 재시험한 것은 아니다.

## 4. 로컬 백엔드 실행 및 페이지 오류 분석

### 일부 페이지의 404

- 프런트엔드의 `/api` 요청은 로컬 `http://127.0.0.1:5000`으로 전달되는 구성이다.
- 당시 5000 포트는 기존 Docker `telecom-api` 컨테이너가 사용 중이었다.
- 컨테이너는 10월 21일 생성됐으며 로컬 소스 폴더가 마운트돼 있지 않았다.
- 로컬 최신 소스에는 공지사항·포인트 상점·Zabbix API가 있지만, 실행 중인 컨테이너의 라우트 목록에는 해당 경로가 없었다.
- 따라서 새 화면과 이전 백엔드 버전의 불일치로 일부 페이지가 404를 반환했다.

### 최신 소스 실행 후 로그인 실패

- Docker를 중지하고 로컬 Flask를 실행하면 사용하는 DB 설정도 달라졌다.
- Docker는 `host.docker.internal`의 PC2 DB, 로컬 루트 `.env`는 `192.168.3.18`의 DB를 가리켰다.
- 읽기 전용 조회로 확인한 당시 상태:
  - `192.168.3.18`: `read_only=1`, `super_read_only=1`
  - PC2 `127.0.0.1`: `read_only=0`, `super_read_only=0`
- 로그인 시 세션·접속 이력 저장이 필요해 읽기 전용 DB에서는 오류가 발생할 수 있음을 설명했다.
- `.env` 파일을 바꾸지 않고 현재 PowerShell에만 DB 호스트를 지정하는 실행 방법을 안내했다.

```powershell
cd "C:\Users\user\Desktop\Project\telecom-security-project\backend"
$env:DB_HOST = "127.0.0.1"
python -m flask --app wsgi:app run --host 127.0.0.1 --port 5000
```

> 기존 Docker API와 로컬 Flask는 같은 5000 포트를 동시에 사용할 수 없다. `python app.py`는 현재 폴더에 없는 `cert.pem`·`key.pem`을 요구하므로 이 로컬 확인에서는 위 Flask 실행 방법을 안내했다. 사용자 계정 생성·권한 변경·DB 초기화는 수행하지 않았다.
