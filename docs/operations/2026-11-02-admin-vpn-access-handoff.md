# 관리자 웹의 내부 PC·VPN 접근 제한 적용 기록

작성일: 2026-11-02 (Asia/Seoul)  
대상: PC3 pfSense/OpenVPN, PC1에서 관리하는 k3s 공개 edge  
상태: **설정 적용 및 PC3 응답 검증 완료 / 실제 VPN·비허용 PC 시험 등 일부 미완료**

이 문서는 오늘의 현장 작업을 정리한 공개용 인수인계 기록이다. 내부 주소, VPN 대역, 포트 매핑, 인증서 지문, 개인키, 자격증명, 생 로그 및 실제 백업 경로는 별도의 비공개 인수인계 자료에서 관리한다.

## 1. 목표와 적용 범위

고객 웹은 공개 진입점으로 계속 제공하면서, 프로젝트 관리자 화면과 관리자 API는 관리 전용 입구를 이용하도록 분리했다. pfSense에서 관리 입구의 허용 출발지를 PC1·PC2·PC3와 승인된 OpenVPN 터널로 설정했다.

- 공개 차단 대상: `/admin`, `/admin/` 이하, `/api/admin`, `/api/admin/` 이하.
- 관리 전용 입구에서는 기존 세션·ADMIN 역할·CSRF 검사를 유지한다.
- VPN 네트워크 허용과 프로젝트 ADMIN 권한 부여는 별개다.
- DB 준비 상태와 기존 관제 웹 응답을 함께 점검했다.

이 결과는 pfSense를 경유하는 관리 입구의 정책과 확인한 공개 경로에 대한 것이다. 모든 직접 접근 경로나 모든 사용자 역할의 실증까지 완료한 것으로 해석하지 않는다.

## 2. PC3 pfSense·OpenVPN 적용

### 사전 점검과 원본 보존

현재 NAT, 연계 방화벽 규칙, Hybrid Outbound NAT, HAProxy listener, OpenVPN 서버의 터널·배포 경로를 읽기 전용으로 대조했다. 변경 전 전체 pfSense 구성을 비공개 파일로 백업했다.

기존 관리 규칙은 PC3 한 대만 대상으로 했고, VPN 내부에는 현재 관리 서비스와 맞지 않는 과거 GUI 허용이 남아 있었다. VPN 반환에는 자동 Outbound NAT가 이미 존재했다.

### 실제 변경

| 항목 | 적용 내용 |
|---|---|
| 관리자 PC 그룹 | PC1·PC2·PC3를 별도 관리자용 Host alias로 구성 |
| VPN 그룹 | 실제 승인된 터널 대역을 별도 Network alias로 구성 |
| 기존 관리 NAT | PC3 전용 Source를 세 PC 그룹으로 확대하고 연계 WAN Pass를 확인 |
| VPN 관리 NAT | VPN 진입 인터페이스용 규칙을 별도로 추가하고 관리 웹 대상만 허용 |
| PC 반환 경로 | 기존 관리 SNAT의 Source를 세 PC 그룹에 맞춤 |
| VPN 반환 경로 | 기존 자동 NAT를 사용하며 중복 전용 SNAT는 추가하지 않음 |
| VPN 경로 배포 | 기존 배포 경로를 보존하면서 관리 접속 주소의 경로 추가 |
| VPN 인증 입구 | 과거 단일 원본 제한을 정리하고 기존 인증서·사용자 인증 방식 유지 |
| 과거 VPN GUI 허용 | 사용 중인 서비스와 맞지 않는 규칙을 삭제 대신 비활성화 |

연계 관리 WAN Pass의 Gateway default와 기존 반환 옵션을 확인했다. Floating 규칙 목록에는 별도 규칙이 없었다. Save/Apply 성공과 변경 대기 표시 해제를 확인했다.

VPN 인증 포트를 허용하는 것과 터널 내부 관리 웹을 허용하는 것은 다른 규칙이다. VPN 클라이언트는 연결을 다시 맺어 추가된 경로를 받아야 한다.

## 3. PC1 공개 edge 적용과 오류 해결

### 최초 중단

최초 적용 도구는 공개 웹·API의 `proxy_pass`에 기본 서비스 이름이 직접 표기돼 있을 것으로 기대했다. 실제 배포는 노드 로컬 서비스 이름을 사용해 다음 검사에서 중단됐다.

```text
STOP: Expected exactly one known public web/API server.
```

이 중단은 ConfigMap 변경과 edge 재시작 이전에 발생했다. 검사를 지우고 강제 적용하지 않았다.

### 구조 조회와 v3 수정

읽기 전용 `inspect` 기능으로 실제 listen·location·proxy 대상 구조를 확인했다. 조회 기능은 헤더 값, URL 자격증명·쿼리 문자열, 개인키와 전체 설정을 출력하지 않도록 했다.

v2는 검증 가능한 upstream 별칭·서비스 DNS 표기를 지원했다. 현장 조회로 확인된 노드 로컬 서비스 이름은 v3에 명시적으로 반영했다. 기존 proxy 대상과 노드 로컬 전달 정책은 보존했다.

최종 도구는 다음 순서로 동작하도록 구성했다.

1. 두 공개 edge가 Ready이고 두 노드에 배치됐는지 확인.
2. 알려진 공개 웹·API 서비스와 기존 내부 API 차단 구조를 확인.
3. 공개 관리자 경로 네 곳의 차단만 추가한 후보 생성.
4. 두 실행 edge에서 후보 `nginx -t` 검사.
5. 원본을 비공개로 백업하고 ConfigMap 버전·체크섬을 확인한 뒤 해당 설정 키만 갱신.
6. 공개 edge를 하나씩 교체하고 준비 상태 확인.
7. 교체 실패 시 검증된 원본 복구를 시도하며, 동시 작업자의 변경은 강제로 덮어쓰지 않음.

도구의 로컬 검사 **18개**와 Python 문법 검사를 통과했다. 검사에는 현장 서비스명 재현, 원본 보존·멱등성, 알 수 없는 대상·namespace·포트 거부, 내부 차단 보존과 동시 변경 거부를 포함했다. 앱 전체 테스트나 실제 서버 롤백 실증을 수행한 결과는 아니다.

### 실제 적용 보고

PC1 담당자가 SSH·sudo 인증 후 v3를 실행했고 다음 결과를 전달했다.

```text
PLAN OK: only four public admin path denials; nginx -t passed on both edges.
APPLIED: two public edges Ready. External 404/customer/private-admin tests required.
```

따라서 실제 서버의 두 edge 문법 검사와 적용 성공은 사용자 실행 결과로 확인했다. 이후 웹 응답은 PC3에서 별도로 조회했다. 서버 원본 백업과 pfSense 전체 백업의 실제 위치는 비공개 기록에 보존했다.

## 4. 적용 후 PC3 실측 결과

CA·주소 검증을 유지한 요청으로 확인했다. 실습 CA의 폐기정보 미제공에는 `--ssl-revoke-best-effort`를 사용했고 `-k`는 사용하지 않았다. 양 노드의 공개 edge 직접 검사는 `--connect-to`로 연결 대상만 바꾸고 원래 서비스 호스트에 대한 인증서 검증을 유지했다.

| 검사 | 실제 결과 |
|---|---|
| 공개 `/admin` | 404 |
| 공개 `/admin/customers` | 404 |
| 공개 `/api/admin/dashboard` | 404 |
| 공개 `/api/admin/monitoring-links` | 404 |
| 공개 고객 웹 `/` | 200 |
| 공개 `/api/health/ready` | database/status ok |
| 관리 전용 `/admin` | 200 |
| 관리 전용 관리자 API 미인증 요청 | 401 |
| 기존 공개 보조 입구의 `/admin` | 404 |
| HAProxy 시험 입구의 `/admin` | 404 |
| PC1 공개 edge 직접 확인 | 404 |
| PC2 공개 edge 직접 확인 | 404 |
| Graylog 웹 | 200 |
| Wazuh HTTPS | 302 로그인 응답 |

관리 화면의 200은 HTML 전달 확인이며 실제 ADMIN 로그인 성공을 의미하지 않는다. 미인증401은 해당 검사에서 인증 요구가 유지됐다는 결과다. 과거의 앱 IP 차단은 이 미인증 검사에서 재현되지 않았지만 모든 IP 차단 원인이 영구 해소됐다고 판단하지 않는다.

## 5. 담당자 인수인계

- 관리자 작업은 팀에서 별도 전달한 **관리 전용 주소**로 접속한다. 공개 주소의 관리자 경로404는 의도한 동작이다.
- PC1·PC2·PC3의 네트워크 허용과 프로젝트 계정 인증을 구분한다.
- VPN 사용자는 재연결 후 관리 주소 경로와 실제 로그인을 확인한다.
- 변경 당시의 실제 주소·규칙 값·원본 백업·스크립트는 비공개 인수인계 자료를 따른다.
- 복구 시 ConfigMap 원본과 공개 edge의 순차 교체를 함께 다룬다. Deployment의 rollout undo만으로 ConfigMap 내용이 복구되지는 않는다.
- 현재 배포와 저장소 예시 설정의 차이를 확인하고, 예시 파일 전체를 운영 설정에 덮어쓰지 않는다.

## 6. 남은 검증과 제한

- [ ] PC1·PC2에서 관리 전용 주소의 실제 ADMIN 로그인·조회·새로고침 확인.
- [ ] 실제 외부 VPN 클라이언트의 연결·경로 수신·관리자 로그인 확인.
- [ ] 비허용 PC에서 관리 입구의 **새 연결**이 차단되는지 확인.
- [ ] 관리 입구에서 CUSTOMER 역할 거부와 기존 세션·CSRF 동작 확인.
- [ ] 고객 로그인·업무 읽기/쓰기 회귀 확인.
- [ ] 관리 NodePort·별도 API 호스트 등 pfSense를 거치지 않는 우회 경로의 제한 확인.
- [ ] 다중 이용자의 공유 NAT 주소와 앱 자동 IP 차단의 상호 영향 확인.
- [ ] 실제 로그 수집·에이전트·알림 파이프라인 회귀 확인.
- [ ] 재부팅 후 정책 유지 및 비공개 백업을 이용한 복구 검증.

고객 웹·DB 준비 상태·관제 웹 응답은 이번에 실측했다. 위 미실행 항목을 완료 처리하지 않으며, 전체 무중단·모든 우회 경로 차단·모든 역할의 기능 회귀 완료를 주장하지 않는다.
