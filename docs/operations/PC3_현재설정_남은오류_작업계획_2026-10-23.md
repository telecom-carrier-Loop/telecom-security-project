# PC3 현재 설정·남은 오류·작업 계획

작성 기준: 2026-10-23, Asia/Seoul  
대상: 통신사 보안 프로젝트 / PC3 Windows 및 VMware의 C-pfsense VM  
범위: 현재 적용한 설정, 아직 남은 오류와 미검증 사항, 앞으로 할 일. 해결한 오류의 발생·처리 이력은 제외한다.

## 1. 현재 구성과 역할

PC3의 pfSense는 프로젝트 웹서비스의 접속 창구와 포트포워딩을 담당한다. PC1·PC2 VM의 기존 IP와 k3s 연결은 유지한다. 노드의 모든 인터넷 통신을 pfSense로 통과시키는 구성은 아니다.

```text
PC3 Windows: 192.168.3.20/24
  │ 192.168.7.178/32 영구 직접 경로
  ▼
pfSense WAN: 192.168.7.178:8080
  │ 목적지 변환 + 응답 경로용 출발지 변환
  ▼
PC1 Ubuntu VM: 192.168.7.185:30080
  ▼
k3s telecom-web → API → DB

별도 관리 경로:
PC3 VMnet4: 192.168.50.100/24
  → pfSense LAN: https://192.168.50.1
```

### 주소와 접속점

| 대상 | 현재 값 | 용도 / 상태 |
|---|---|---|
| PC3 실제 이더넷 | 192.168.3.20/24 | Windows 호스트 주소 |
| PC3 기본 게이트웨이 | 192.168.3.1 | 기존 값 유지 |
| pfSense WAN | 192.168.7.178/24 | DHCP로 할당받은 서비스 진입 주소 |
| pfSense WAN 게이트웨이 | 192.168.7.1 | 실제 적용된 라우팅 규칙 출력에서 확인 |
| pfSense LAN | 192.168.50.1/24 | PC3 내부 관리망 |
| PC3 VMnet4 | 192.168.50.100/24 | 기본 게이트웨이·DNS 비워 둠 |
| PC1 프로젝트 VM | 192.168.7.185 | k3s server, 웹 NodePort 30080 |
| PC2 프로젝트 VM | 192.168.7.100 | k3s agent |
| 현재 웹 접속 주소 | http://192.168.7.178:8080 | HTTP 응답 확인 완료 |
| pfSense 관리 주소 | https://192.168.50.1 | 관리 화면 로그인 확인 완료 |

pfSense 관리 화면의 HTTPS와 프로젝트 웹서비스의 HTTPS는 별개다. 관리 화면이 HTTPS로 열린다고 웹서비스의 TLS·로그인이 준비된 것은 아니다.

## 2. PC3에서 적용한 설정

### 2.1 VMware와 pfSense VM

| 항목 | 현재 설정 |
|---|---|
| VM 이름 | C-pfsense |
| pfSense 버전 | 2.7.2-RELEASE amd64 |
| VM 자원 | CPU 2개, RAM 2GB |
| VMnet0 | 실제 Realtek 유선 랜카드에 Bridged |
| VMnet4 | Host-only, 192.168.50.0/24 |
| VMnet4 호스트 가상 어댑터 | 활성화 |
| VMnet4의 VMware DHCP | 비활성화 |
| Network Adapter 1 | Custom: VMnet0 → WAN em0 |
| Network Adapter 2 | Custom: VMnet4 → LAN em1 |
| Network Adapter 3 | 연결 및 시작 시 연결 해제 |
| 이전 DMZ·WAS·DB·SEC 인터페이스 | 설정은 남아 있고 연결은 비활성 상태 |

VMware DHCP와 pfSense 자체 LAN DHCP는 서로 다르다. pfSense LAN DHCP의 현재 사용 여부·범위는 별도 확인이 필요하다.

### 2.2 WAN·LAN 기본 설정

- WAN IPv4: DHCP, 확인된 주소 192.168.7.178/24.
- WAN의 `Block private networks and loopback addresses`: 해제.
- `Block bogon networks`: 체크 유지.
- LAN IPv4: 192.168.50.1/24.
- Windows VMnet4 IPv4: 192.168.50.100/24, 기본 게이트웨이·DNS 없음.
- PC1·PC2의 노드 IP, 기본 게이트웨이, k3s 구성은 이번 PC3 경로 작업에서 변경하지 않았다.

### 2.3 웹 포트포워딩

pfSense 메뉴: Firewall → NAT → Port Forward.

| 항목 | 적용 값 |
|---|---|
| Interface / Address Family | WAN / IPv4 |
| Protocol | TCP |
| Source / Source port | any / any |
| Destination | WAN address |
| Destination port From / To | 8080 / 8080 |
| Redirect target IP | 192.168.7.185 |
| Redirect target port | 30080 |
| Description | telecom-web |
| NAT reflection | Disable |
| Filter rule association | 연계 허용 규칙 생성 |

연계 WAN 허용 규칙은 TCP → 192.168.7.185:30080을 허용한다. 실제 규칙 출력에서 `reply-to`가 없는 것을 확인했다. Gateway는 default를 사용한다.

### 2.4 응답 경로용 Outbound NAT

pfSense 메뉴: Firewall → NAT → Outbound. 모드는 **Hybrid Outbound NAT**다.

| 규칙 | Interface | Source | Destination | Destination port | Translation |
|---|---|---|---|---|---|
| 학원 프로젝트망용 | WAN | 192.168.7.0/24 | 192.168.7.185/32 | TCP 30080 | WAN address |
| PC3 실제 유선망용 | WAN | 192.168.3.0/24 | 192.168.7.185/32 | TCP 30080 | WAN address |

- 두 규칙의 Source port와 Translation port는 빈칸이다.
- Static Port는 체크하지 않는다.
- 실제 적용된 NAT 규칙 출력에서도 두 규칙을 확인했다.
- 이 출발지 변환 때문에 서버·앱에서 실제 사용자 IP 대신 pfSense 주소가 보일 수 있다.

### 2.5 PC3 Windows의 영구 정적 경로

pfSense WAN 주소 한 대에만 실제 이더넷으로 직접 연결하도록 설정했다.

| 항목 | 적용 값 |
|---|---|
| DestinationPrefix | 192.168.7.178/32 |
| NextHop | 0.0.0.0 — On-link, 직접 연결 |
| Interface | 실제 이더넷 / ifIndex 21 |
| RouteMetric | 5 |
| 저장 | ActiveStore·PersistentStore 모두 확인 |
| PC3 IP·기본 게이트웨이 | 192.168.3.20/24·192.168.3.1 유지 |

적용한 명령은 다음과 같다. **현재 PC3에는 이미 저장돼 있으므로 다시 추가할 필요가 없다.**

```powershell
netsh interface ipv4 add route prefix=192.168.7.178/32 interface=21 nexthop=0.0.0.0 metric=5 store=persistent
```

조회:

```powershell
route print -4
```

원복이 필요한 경우에만 관리자 PowerShell에서 다음 명령을 사용한다.

```powershell
netsh interface ipv4 delete route prefix=192.168.7.178/32 interface=21 nexthop=0.0.0.0 store=persistent
```

이 경로는 PC3 한 대에만 적용된다. 다른 PC에 자동으로 적용되지 않으며, pfSense WAN 주소나 실제 랜카드가 바뀌면 경로도 재확인해야 한다. 다른 PC에서 인터페이스 번호 21을 그대로 사용하면 안 된다.

## 3. 현재 남은 오류

### 3.1 웹 화면의 “인증이 필요합니다”

**상태: 미해결, 정확한 원인 추가 확인 필요.**

- 사용자 화면에서 데이터 조회 대신 “인증이 필요합니다”가 표시되는 것을 확인했다.
- 유효한 로그인 세션을 서버가 받지 못하는 상태로 판단한다.
- 로그인 성공 후 발생하는지, 로그인 전 발생하는지는 아직 확인하지 못했다.
- 미로그인·세션 만료 가능성과 함께, 현재 HTTP 접속에서 Secure 쿠키가 저장·전송되지 않는 가능성을 확인해야 한다.
- 현재 프로젝트 소스는 `__Host-telecom_session` 쿠키에 Secure·HttpOnly·SameSite=Lax를 사용한다. HTTP LAN 주소에서 이 쿠키를 사용하는 인증을 완료했다고 판단하면 안 된다.
- 실제 브라우저의 로그인 응답·후속 API 응답·쿠키 전달 상태를 확인하기 전에는 원인을 확정하지 않는다. 쿠키 값이나 비밀번호는 공유하지 않는다.

**DB 점검 결과:** `http://192.168.7.185:30080/api/health/ready`에서 HTTP 200과 아래 응답을 확인했다.

```json
{"data":{"database":"ok","status":"ok"},"success":true}
```

위 내용은 응답 중 상태 필드를 발췌한 것이다. `/api/health/live`도 HTTP 200으로 응답했다. 따라서 현재 화면을 DB 전체 접속 불가로 단정하지 않는다. 다만 기본 DB 접속 확인이 모든 테이블·업무 쿼리·복제 정상까지 보장하지는 않는다.

### 3.2 HTTPS 웹서비스 미적용

**상태: 준비 파일 작성·로컬 검사 완료, 실제 서버 미적용.**

- 현재 서비스 진입점은 HTTP 8080이다.
- HTTPS edge 템플릿, API 프록시 및 적용 절차를 준비했다.
- TLS 서버 인증서, 클라이언트의 CA 신뢰, 서버 배포와 pfSense 새 규칙은 아직 적용하지 않았다.
- Secure 쿠키·Origin·CSRF 검사를 완화해서 우회하지 않고 HTTPS 환경에서 로그인과 데이터 조회를 검증한다.

## 4. 앞으로 해야 할 일

### 우선순위 1 — 인증 오류 구간 확인

1. 사용자가 어떤 주소로 접속하고 로그인했는지 확인한다.
2. 로그인 요청의 상태 코드·오류 메시지와 다음 API 요청을 비교한다.
3. 로그인 성공 응답 이후 브라우저가 세션 쿠키를 보관·전송하는지 확인한다.
4. 원인이 확인되면 HTTPS·프록시 설정과 함께 수정한다. DB 주소를 추측해서 바꾸지 않는다.

### 우선순위 2 — PC1 서버의 HTTPS 준비

이 단계는 PC3 설정 전에 필요한 서버 작업이다. 사용자가 서버 접속을 확인하기로 했으며, 현재 원격 적용은 하지 않았다.

1. PC1 SSH 접속·서버 지문·실행 권한을 확인한다.
2. 현재 Web/API Service 포트, Ready Endpoint, NetworkPolicy, API 프록시 신뢰 설정을 확인한다.
3. NodePort 30443이 기존 서비스와 충돌하지 않는지 확인한다.
4. 실제 사용할 IP 또는 DNS 이름이 SAN에 포함된 TLS 인증서를 준비한다.
5. 준비한 `school-lab-edge` 프로필을 검토·적용한다. 기존 Web/API 이미지·DB·Secret·k3s 노드 설정을 이전 예시 값으로 덮어쓰지 않는다.
6. edge 준비 상태와 클러스터 내부 Web/API 연결을 확인한다.

### 우선순위 3 — PC3 pfSense의 HTTPS 포워딩 추가

**아래는 향후 적용 예정 값이며 현재 적용된 규칙이 아니다.** PC1 서버 준비 완료 후 진행한다.

| 항목 | 예정 값 |
|---|---|
| 브라우저 접속 | https://192.168.7.178:8443 |
| pfSense WAN 수신 | TCP 8443 |
| 포워딩 대상 | 192.168.7.185:30443 |
| Outbound NAT | 기존 두 Source 대역에 대해 목적지 포트 30443인 규칙 추가 |
| NAT Translation | WAN address |

연계 WAN Pass 규칙을 추가하고 Disable Reply-To와 Gateway default를 확인한다. 기존 HTTP 8080 규칙은 HTTPS 검증 전까지 유지한다. API 30500·DB 3306·k3s 6443은 웹서비스용 WAN 포워딩에 추가하지 않는다.

### 우선순위 4 — PC3 브라우저에서 HTTPS·로그인 검증

1. 인증서 발급 CA를 확인하고 PC3에 필요한 신뢰 설정을 적용한다.
2. 인증서 오류를 무시하지 않고 실제 HTTPS 주소로 접속한다.
3. API 준비 상태가 JSON으로 정상 응답하는지 확인한다.
4. 로그인 → 데이터 조회 → 새로고침 → 로그아웃을 확인한다.
5. 공개 경로에서 `/admin`, `/api/admin`, `/api/internal` 및 하위 경로가 차단되는지 확인한다. 관리 기능은 별도 승인된 관리 경로가 필요하다.
6. 검증 후 HTTP 8080을 유지할지, 닫거나 HTTPS로 이동시킬지 정한다.

### 우선순위 5 — 주소·관리 설정과 백업

| 할 일 | 담당 범위 / 주의점 |
|---|---|
| pfSense WAN 주소 예약 | 학원 DHCP 관리자와 192.168.7.178의 예약 여부 확인. 임의의 주소로 변경하지 않음 |
| 노드 주소 고정·예약 확인 | PC1·PC2 실제 서버 설정 확인 후 진행 |
| 관리망 DHCP 확인 | pfSense LAN DHCP 사용 여부·범위를 확인하고 Windows VMnet4의 192.168.50.100과 중복되지 않게 함 |
| pfSense 설정 백업 | Diagnostics → Backup & Restore에서 보관. 백업에는 민감정보가 포함될 수 있으므로 공개 저장소·채팅에 업로드하지 않음 |
| 이전 인터페이스 정리 | 백업 후 DMZ·WAS·DB·SEC와 연결된 규칙·DHCP·서비스 의존성을 확인하고 불필요한 설정만 정리 |
| 재부팅 후 확인 | 영향 시간을 정한 뒤 PC3·VM 기동, pfSense WAN 주소, Windows 영구 경로, 웹·관리 접속 유지 확인 |

## 5. 별도로 남겨둘 설계·검증 사항

아래는 확인된 장애가 아니라 현재 구성의 범위와 한계다.

- **직접 접근 경로:** 같은 학원망에서 노드 NodePort로 직접 접근할 수 있다. pfSense가 모든 VM 통신을 강제 통제하는 구성으로 보고하지 않는다.
- **실제 사용자 IP:** SNAT로 앱에 pfSense IP가 보일 수 있다. IP 기반 차단·접속 제한·관제 시험 전에 실제 출발지 주소를 확인한다.
- **장애 전환:** 현재 포워딩 대상은 PC1 한 대다. PC1 전체 장애 시 PC2 자동 전환은 구성하지 않았다. 필요하면 별도 설계한다.
- **다른 PC의 접속:** PC3의 정적 경로는 다른 Windows PC에 적용되지 않는다. 각 PC의 IP와 경로를 별도로 확인한다.
- **기존 VLAN·DB VIP:** 현재 VM에 이전 주소를 다시 할당하거나 DB 설정을 임의로 변경하지 않는다.

## 6. 완료 판단 기준

- [ ] 실제 HTTPS 웹 주소가 인증서 검증을 통과해 열린다.
- [ ] 같은 주소에서 로그인 후 데이터가 조회되고 새로고침 후에도 세션이 유지된다.
- [ ] 공개 API와 관리·내부 API의 접근 경계를 확인한다.
- [ ] WAN·노드 주소 유지 방안과 PC3 영구 경로를 확인한다.
- [ ] 관리망 IP 중복 가능성과 불필요한 이전 설정을 점검한다.
- [ ] pfSense 백업을 보관하고 재기동 후 접속 상태를 확인한다.

현재 완료된 HTTP 접속과 DB 기본 연결 확인을 위 전체 항목의 완료로 해석하지 않는다.
