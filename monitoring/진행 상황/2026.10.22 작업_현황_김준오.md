## 2. K09: 패킷·트래픽 분석 구현 및 검증

### 2.1 실행 환경

- **Windows:** Docker에서 Graylog 관리 화면 `http://localhost:9000`, GELF UDP Input `12201` 사용.
- **Kali:** Windows PowerShell로 접근하는 WSL2 Kali Linux, 인터페이스 `eth0`, 표시된 주소 `172.31.217.61/20`.
- **분석기 경로:** `/root/K09/K09_packet_traffic_analysis/pcap_to_graylog.py`.
- 명령어 실행 위치를 구분함: `PS C:\Users\user>`는 Windows PowerShell, `root㉿DESKTOP-IMHN3JN` 프롬프트는 Kali Linux 셸.

### 2.2 패킷 수집

첫 시도에서 `tcpdump`의 캡처 결과가 0건이었으나, 캡처 중 Kali에서 `ping -c 10 1.1.1.1`과 `curl -I https://example.com`으로 정상 트래픽을 발생시켜 재수집했다.

```bash
cd ~/K09/K09_packet_traffic_analysis
sudo timeout 30 tcpdump -i eth0 -nn -s 128 -w traffic.pcap 'ip' &
CAPTURE_PID=$!
sleep 2
ping -c 10 1.1.1.1
curl -I --connect-timeout 5 --max-time 10 https://example.com
wait $CAPTURE_PID
sudo tcpdump -nn -r traffic.pcap -c 10
```

실제 명령 출력: **45 packets captured / 45 received by filter / 0 dropped by kernel**. `ping`은 10회 전송, 9회 응답(10% ICMP 응답 손실)이었다. 이 응답 손실은 tcpdump의 커널 캡처 손실과 다른 지표다. `timeout` 종료 코드 124는 지정된 30초 종료로 인해 나타날 수 있다.

### 2.3 Python 분석 결과

```bash
python3 pcap_to_graylog.py --pcap traffic.pcap --dry-run
```

| 출발지 IP | 패킷 수 | TCP SYN | ICMP | 목적지 포트 종류 |
|---|---:|---:|---:|---:|
| `172.31.217.61` | 24 | 1 | 10 | 1 |
| `172.66.147.243` | 12 | 0 | 0 | 1 |
| `1.1.1.1` | 9 | 0 | 9 | 0 |
| **합계** | **45** | **1** | **19** | — |

분석 결과는 총 3개의 출발지 IP 요약 로그다. `count()`가 집계하는 요약 로그 수와 `packet_count`의 실제 패킷 수를 혼동하지 않도록 했다.

### 2.4 Graylog 전송과 확인

Kali 셸에서 아래와 같이 분석 로그를 전송했고 Graylog Search 화면에서 `k09-pcap-analyzer`가 보이는 **3건의 요약 메시지를 확인**했다.

```bash
python3 pcap_to_graylog.py --pcap traffic.pcap --graylog-host 127.0.0.1 --graylog-port 12201
```

Graylog 검색어:

```text
rule:packet-traffic-analysis
```

K09 Event Definition으로는 다음 3개를 구성했다.

| 규칙 | 목적 | 조건(기본값) |
|---|---|---|
| `ED-K09-01` | 다중 포트 접근 | `unique_dst_ports:[20 TO *]` |
| `ED-K09-02` | TCP SYN 급증 | `tcp_syn_count:[100 TO *]` |
| `ED-K09-03` | IP별 패킷 과다 | `packet_count:[500 TO *]` |

**유의:** 45패킷 실측 결과는 기본 임계치를 충족하지 않는다. 이후 작성한 K09 모의 통계 코드로 임계치/이벤트 흐름을 시험하는 것과 실제 트래픽 기준의 공격 판정은 구별한다.

서버 반영 후 **`/var/ossec/bin/wazuh-analysisd -t` 규칙 검사 성공 → Manager 재시작 → Agent 그룹 배정·로그 확인**이 필요하다. 대화에 실제 검사 성공 출력이나 신규 Linux Agent 등록·탐지 성공 증빙은 아직 없다.

## 5. n8n · Discord 메시지 구성

### 5.1 기존 운영 경로 보존

- 사용자 요청에 따라 **기존 1~9번 정상 동작 경로와 의도적으로 비활성화한 HTTP API 노드**는 유지하는 것을 기준으로 작업했다.
- 새로운 경로는 K09 `packet-traffic-alert`, EX `security-scenario-alert`와 통합 Discord 전송 노드에 연결하도록 설계했다.
- Graylog Docker가 Windows n8n에 접근할 때의 주소 `http://host.docker.internal:5678/webhook/...`는 그대로 사용 가능하나, 새로운 k3s Flask API 주소는 별도 변경이 필요하다.

### 5.2 Discord 메시지 노드 문제 및 수정

- 처음 통합 메시지 코드를 적용한 후 Discord에 **`[MEDIUM] 보안 이벤트`**와 함께 계정명 **`Security Alert Bot`**이 표시되는 화면이 나왔다.
- 원인으로, 앞단 Code 노드가 이미 `username`·`embeds` 형태의 Discord 완성 메시지를 만들고 이를 공통 Set `메시지` 노드가 보안 이벤트로 **재해석**하는 구조를 확인했다.
- K09와 EX의 개별 Code 노드에서 Discord 완성 메시지를 **바로 `디스코드` HTTP Request 노드로 보내자**, EX 공통 경로에서 `ED-WZ-02 | Linux 호스트 보안 탐지 (100230~100237)`가 Discord에 표기된 화면을 확인했다.
- 이후 권장 구조를 **Webhook → Code(필드 정규화·분류) → 공통 `메시지` Set(Discord Embed 생성) → Discord HTTP Request**로 정리하고, K09 및 EX 판정함수 교체 코드를 제안했다.

> **실제 확인 범위:** EX 경로 Discord 메시지 수신 및 n8n 실행 화면은 확인했다. 다만 이후 제안한 **공통 메시지 경유 구조를 적용한 최종 실행 성공 화면은 아직 확인하지 못했다.** `ED-WZ-02` Discord 경보 역시 실제 Wazuh Manager 발동을 증명하지 않는다.

### 5.3 메시지 표준 필드

- 공통 필드: `source`, `kind`, `event_definition`, `rule`, `severity`, `decision`, `reason`, `event_id`, `event_key`.
- K09: `packet_count`, `tcp_syn_count`, `tcp_rst_count`, `unique_dst_ports`, `unique_dst_ips` 등.
- Wazuh: `rule_id`, `agent`, `file`, `rule_level`, `fim_event` 등(상위 Webhook에서 전달하는 경우에 한함).
- 계정 브루트포스(ED-08)는 계정명 중심으로 출력하고 없는 IP를 필수 요구하지 않음.
- 수집되지 않은 횟수·IP·Rule ID를 임의 생성하지 않도록 설계.

## 6. PC1·PC2 Linux VM / k3s 이전 대응

새 인프라 계획은 **PC1과 PC2 각각 VMware Linux VM을 만들고 두 VM을 하나의 k3s Kubernetes 클러스터로 구성해 Flask 웹 이미지를 배포**하는 것.

| 시스템 | 변경/검토 항목 |
|---|---|
| Wazuh | Linux 노드 Agent 등록, 감사/파일 감시 경로, Windows Agent와 그룹 분리 |
| Graylog | 신규 VM·Pod·Ingress 로그 전송기, 호스트 IP·수집 포트, 규칙 필드 정규화 |
| n8n | Flask API 호출 대상을 Kubernetes Ingress/외부 노출 주소로 변경. 기존 Graylog → n8n Webhook 경로는 원칙적으로 유지 |
| Zabbix | 두 Linux 노드와 웹 상태 감시 항목 추가 |
| Flask | DB 연결, 쿠키/CORS, Ingress 뒤 프록시 동작, 환경변수 확인 |
| pfSense | 새 웹 진입점으로 포트포워딩과 필요한 통신 정책 갱신 |

**기술적 주의:** k3s는 기본적으로 containerd를 사용하므로 Docker 전용 수집 설정을 그대로 쓰지 않는다. Fluent Bit 등 노드 로그 수집기와 Kubernetes/Ingress 감사·접근 로그 수집 구성이 별도 필요하다. `localhost`/`host.docker.internal`은 새 VM의 Flask를 자동으로 가리키지 않는다.

**현재 상태:** 구조 및 연동 계획과 관련 파일 작성 단계. PC1·PC2 클러스터 구축·실배포·접속 및 중앙 수집 성공 출력은 공유되지 않았다.
